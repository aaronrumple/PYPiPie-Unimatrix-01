Overview

Copy parameter values from elements of one category to related elements of another — or between parameters of the same element — automatically on save, sync, print and export.

Mappings live in the project

Stored as Extensible Storage, so they travel with the model and sync to central.

Type-safe

Every pair is checked: exact, converts, lossy or incompatible. Units are handled for you.

Rules

Small sandboxed Python snippets transform a value: switch/case, math, if/then, regex.

Hands-off

Runs on save, sync, print and export — silently, without touching unchanged values.

2Quick start

Example: copy each room's Department to the doors in that room.

  1. Click Map Parameters.
  2. In column A · Source category pick Rooms; in column B · Target category pick Doors.
  3. The relationship switches to Room → elements in room automatically.
  4. Select Department in the A list. The B list now shows a badge on every parameter (✓ exact, ↻ converts, …).
  5. Select the target parameter in B and click Add pair A → B (or double-click).
  6. Optionally give it a name, then click Apply mapping. It's saved to the project.
  7. Click Push Now to run it immediately — or just save/sync.

The dialog stays open after Apply so you can build the next mapping straight away.

One mapping per category pairing

A mapping is a category pairing — A, B and the relationship (plus the key parameters for Matching key value) — holding any number of parameter pairs. There is never more than one mapping for the same pairing:

  • When the categories and relationship you pick already have a mapping, a blue note says so — ℹ Adds to the existing mapping 'Walls → Doors' (3 pairs) — and column B marks each target that pairing already feeds (mapped from Width [Type]).
  • Apply adds your pairs to that mapping. Identical pairs are ignored. If a target is already fed by a different source you choose Replace or Keep existing.
  • Editing a mapping and switching it to a pairing that already exists offers to merge the two.
  • Auto-pair same names skips targets the pairing already feeds.
  • Importing a file folds its mappings into matching pairings too; the file's pairs win on the same target.

Grouping also helps performance: elements are collected and related once per pairing, not once per pair.

4Same category vs different categories

Same category → same category

e.g. Doors → Doors. With Same element, a value is copied to a different parameter on the same element (instance ↔ type works too). Pushing a parameter onto itself on the same element is blocked — it would do nothing.

Other same-category relationships (Matching key value, Parent family → nested, Parent view → dependent views) link two different elements, so the same parameter is allowed.

Category A → category B

e.g. Rooms → Doors. Push into the same-named parameter or any other writable one. Auto-pair same names pairs every compatible same-named parameter in one click.

The heading above the relationship box tells you which mode you're in.

Units

Revit stores lengths in feet, areas in square feet, and so on. When converting between a measured value and a plain Number or Text, Unimatrix 01 uses the project's display units (Manage → Project Units). So a 3000 mm wall in a metric project becomes the number 3000, not 9.84.

Yes/No

Text becomes Yes for yes y true t 1 on x ✓ and No for no n false f 0 off or empty.

An ✕ incompatible pair can still be added if you give it a rule that produces the target value. You'll be asked when you click Add pair.

6bRead-only targets

Read-only parameters are filtered out of the target (B) side so you can't map into something Revit won't let you write.

  • A parameter is hidden from column B if it is read-only on any sampled element or type — computed values (Area, Volume, Perimeter, Length…), formula-driven family parameters, and identity values such as Family, Category, Element ID, Edited by, Host and Room.
  • Read-only-ness that comes from an element's situation doesn't hide a parameter: an element inside a group, or a value locked to a global parameter. Those elements are simply skipped at push time.
  • Every push checks each target element again and counts anything it can't write as read-only target in the results — nothing is attempted, so there are no errors or warnings.
  • Mappings imported from another project whose target is read-only here are flagged in the Mappings list.

7Type & instance parameters

  • A [Type] source parameter is read from the A element's type.
  • A [Type] target parameter is written to the B element's type — this affects every instance of that type.
  • If several instances of one type would write different values to the same type parameter, the first value wins and the others are counted as conflicts.

9Automatic runs

  • Runs are silent: no dialogs. A summary is written to %APPDATA%\pyRevit\Unimatrix01\push.log.
  • Values that are already correct are not rewritten, so elements aren't borrowed needlessly in workshared models.
  • Workshared: elements owned by someone else, or changed in central since you last reloaded, are skipped and counted as blocked.
  • Warnings raised while writing are suppressed. A run that changes nothing leaves no undo entry; one that does adds a single Unimatrix 01: Push parameters step.
  • Family documents, linked models and read-only documents are ignored.

Revit may refuse changes during some print or export paths. When that happens the run is skipped and logged — run Push Now before printing if it matters.

11Import & export

  • Export writes all mappings (or just the selected ones) and settings to a JSON file.
  • Categories are stored by built-in name (OST_Doors), parameters by built-in name, shared-parameter GUID or name, so a file works in other projects.
  • Import → Merge adds the mappings; one with the same id replaces the existing one. Replace all removes current mappings first. You can also take the file's automatic-run settings.
  • Mappings for categories that don't exist in this project are kept but skipped, and flagged in the list.
  • If the file contains rules you're told how many — review them with ƒ before saving.
  • Imported mappings aren't stored until you click Save.

12Mapping rules

A rule is a small piece of Python attached to one pair. It receives the incoming value and decides what gets written. Click ƒ on a pair to add one.

Turning rules on and off

Most mappings don't need a rule, so rules are an optional feature:

  • Project switch — Mapping rules (ƒ) in the Mappings window's options. It starts off in projects with no rules (projects that already contain rules keep it on). When off: rules are kept but never run, the ƒ button is hidden on pairs without a rule, and the rule engine isn't even loaded during save/sync.
  • Per pair — right-click ƒ → Rule on for this pair, or the Rule on for this pair checkbox in the rule editor. A switched-off rule is kept; the pair uses the standard conversion.
  • A pair whose types can't convert on their own (✕ needs rule) only runs while its rule is active; otherwise it is skipped and listed in the results. Adding such a pair while rules are off offers to turn them on.

Two forms

value * 1.10 + 2

# 2. a short script - set (or return) value
if value is None or value == "":
    value = "N/A"
else:
    value = value.upper()

Empty sources

By default a rule is not called when the source is empty: the pair behaves like the standard conversion, so the target is left as it is (or cleared, if Clear targets when source is empty is on). That keeps rules such as value.upper() from failing on elements whose source is blank. Tick Run when the source is empty in the rule editor when the rule should handle blanks itself, e.g. if not value: value = "N/A" — the If / then / else template ticks it for you.

15Rule safety

Rules run unattended on save and sync, and can arrive in files from other people, so they are sandboxed and guarded in three layers.

Sandbox restrictions

  • Not allowed: import, while, def, class, try, with, raise, del, open, eval, exec, getattr and similar.
  • No _private or .NET-style Capitalised attributes; only text/number/list/dict methods.
  • Only plain values go in — rules can't reach the Revit API or the file system.
  • Comprehensions with more than one for ([x for a in A for b in B]) are refused: Revit's IronPython 2.7 silently drops every loop after the first. Write nested for loops instead — a single for plus any number of ifs is fine.

2 · Runtime guards

Every rule is compiled with checks around arithmetic, text building, loops, method calls and regex. If a limit is hit, that element is reported as a rule error and the save continues. See Limits.

3 · Sandbox test

Runs the rule on a background thread, at most 3 seconds, with probe values matched to the source type, each with and without an existing target value:

Numbersempty, 0, 1, −1, 2.5, 0.000001, ±1,000,000, 1e15
Integersempty, 0, 1, −1, 7, ±1,000,000
Yes/Noempty, Yes, No
Text / elementsempty, "", "abc", "A-101", "Level 3", "123", "  padded  ", 2,000 characters

Plus whatever you typed in Incoming value. Verdicts:

  • ✓ passed — every probe ran fine.
  • ⚠ errors — some probes raised errors (often None when the source is empty). Saving is allowed; add an if if your data can look like that.
  • ⛔ guard tripped — saving needs Save anyway.
  • ⛔ didn't finish — can't be saved.

Empty values are only probed when the pair has Run when the source is empty ticked — then handle None first, e.g. if value is None: return SKIP.

17Where settings live

  • All mappings, rules and automatic-run settings are one JSON entity on a DataStorage element named PyPiPie_ParamPusher (original PyPiPie identifiers — Unimatrix 01 was called Data Pusher and PyPiPie before — kept so existing projects keep their mappings).
  • Extensible Storage schema PyPiPieParamPusher, GUID 6b1f6a42-2f6e-4c0e-9a9e-5d3f3f7f1b21, public read/write.
  • Saving mappings is a normal transaction (undoable) and syncs to central like any element.
  • Push log: %APPDATA%\pyRevit\Unimatrix01\push.log (reset at 512 KB).

19Troubleshooting

Nothing happens on save Check Mappings → Run automatically, that the mapping and its pairs are enabled, and look at %APPDATA%\pyRevit\Unimatrix01\push.log. Hooks need pyRevit loaded with the extension enabled.
A parameter I need isn't in the list Only parameters found on the first 60 elements (and their types) are listed. If the category has no elements yet, place one. Column B hides parameters that are read-only on any sampled element (see Read-only targets).
"No related source" for many targets The relationship didn't find an A element. Rooms: is the element inside a placed room in its phase? Keys: do the values really match (spaces, prefixes)?
Many "Blocked" Those elements are borrowed by someone else or changed in central. Reload Latest or ask the owner to sync, then push again.
Pushing into nested families does nothing Look at the per-pair rows. Read-only: the nested parameter is already associated with a parent parameter in the family, so Revit drives it. Missing on target: the nested family doesn't have that parameter. Conflicting: the target is a type parameter and every nested instance shares one nested type, so it can't hold a different value per parent — make it an instance parameter in the nested family and pair to that.
Conflicts on a type parameter Instances of one type have different source values. Push into an instance parameter instead, or use a rule that resolves it.
Lengths come out in the wrong unit Conversions use Project Units. In a rule, value is already in display units. Check the unit settings for that data type.
A rule works in Test but fails in the push Use Preview on model to see real values. Common causes: empty sources (None), text where you expected a number (use num()), or element names that don't exist in the project.
Nothing was pushed during print/export Revit didn't allow changes during that event; it's logged. Run Push Now first.
Dialogs aren't dark Theme following needs Revit 2024 or later. Dialogs pick up the theme when they open.
